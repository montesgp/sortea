# ADR 0021: Client packs and the public copy

Status: accepted, 2026-11-09 (task R2 of the Railway infrastructure work). Complements ADR 0020, "Hosting model".

## Context

The platform is developed and deployed from a private repository, and a public repository keeps a generic copy (ADR 0020). Until now the shared code carried the first client: the seed created it with its real brand, contact, social profiles, site texts, catalog and legal drafts, its images sat in `apps/web/static`, and tests, end-to-end tests and docs used its name, phone and links. Publishing would have needed a manual cleanup every time, and the owner's instruction is that the public repository must hold nothing of a specific client while the private one keeps all of it: "Si el hecho de eliminar desde montesgp/sortea todo lo que tenga que ver con un cliente especifico lo tenemos que hacer si o si. Pero preservar todas esas imagenes y data para el repo privado en [a private account]."

## Decision

- **Shared code is client-neutral.** The seed creates the fictional "Taller Demo" (slug `taller-demo`) with the structure of a real client (brand, theme, contact, CMS blocks, legal drafts, four products, a demo campaign with pending approvals, local accounts) and made-up data, plus the fictional second tenant Pista Sur. Its images are generated placeholders or openly licensed photos with credits. Every test uses Taller Demo or neutral data.
- **A client is a pack.** `clients/<client>/` holds `pack.ts` (a `ClientPack`, `packages/db/src/client-pack.ts`), `static/` with its images, its documents and a README with its operational notes. The seed's organizations are packs too (`packages/db/src/packs`), loaded by the same code.
- **Loading is additive.** `pnpm client:load <client>` creates the organization when it is missing and binds the first of its hosts that no other organization has. An existing organization is left alone unless `--update` is passed; then only its name, settings, theme and CMS blocks are refreshed, each block as a new published version with its revision and legal texts under a new version, as the site editor does. Catalog (unless `--catalog` is passed too, which creates and updates products by slug and never deletes them), campaigns, members and hosts of an existing organization, and every other organization, are never touched. Approvals are always created pending: a pack has no field for them (ADR 0015). The seed follows the same rule, so it can run on a database that already has a client: Taller Demo then takes `demo.localhost`.
- **The local database is the source of a pack's content.** `pnpm client:export <client>` reads the organization from the local database (read-only, local hosts only) and rewrites only the differing values of its `pack.ts`: settings, theme, published blocks, active products, pitches, site FAQs and the real files of its digital products. It never reads orders, buyers, payments, integrations, audit events or members, and never writes a campaign, hosts or members, which stay authored by hand. The files' bytes are copied to `clients/<client>/files/`, kept outside git and the public copy; the pack carries their sha256. A deployed database is private, so the files reach it through the environment's bucket: `pnpm client:upload-files` puts them in `product-assets/_incoming/<sha256>` from the owner's machine, with credentials only in the command's environment, and `client:load` inside the api service moves them to their products after checking the sha256. A deployed load never gets a sample file.
- **Client images keep their URLs.** The web serves every `clients/*/static` directory as part of its static files, in development and in builds (`apps/web/plugins/client-static.ts`), so `/tenants/<client>/...` works where the pack exists and nothing is served where it does not.
- **The public copy is generated, never edited.** `pnpm publish:public` takes the tree of `HEAD`, removes the paths in `.public-exclude` (`clients/`, `odd/`, local tool state), refuses it when any file mentions a client (each `clients/<client>` name and the terms in its `publish-forbidden.txt`), the owner's personal data (`clients/publish-forbidden.txt`) or a CUIT or CUIL number, and otherwise commits it as one commit on top of the public branch. It does not push; a person reviews and pushes. The public history stays as it is.

## Consequences

- Publishing is one command and the check runs every time, so a client mention in shared code is caught before it leaves, not after.
- The private repository's builds include the clients' images; a deployment per client (ADR 0020) can later build with only its own pack if the others' images should not ship with it.
- Tests and end-to-end tests describe the fictional organization. A database that already holds a client gets Taller Demo on `demo.localhost`, so end-to-end runs point `E2E_BASE_URL` there.
- `--update` does not migrate catalog or campaign changes; those stay in the admin, where prices, stock and locked rules are protected.

## Amendment 2026-11-12: several files per product

Owner feedback 2026-11-11b, S2 (decision L2): a ZIP is hard to open on a phone, so a digital product delivers its files directly, one download link each. The pack format follows:

- `files` maps a product either to one file, as before (`{ filename, sha256, contentType }`), or to a list of them in the order buyers get them (`[{ ... }, ...]`). Existing packs stay valid unchanged. A list holds 1 to 10 files, never the same file or download name twice. `contentType` may now also be `image/png` or `image/jpeg`.
- `client:export` writes the single-object form for a product with one file and a list for one with several, ordered by `product_assets.position` (migration 0023), so a pack exported before this change rewrites nothing.
- `client:upload-files` uploads every file of a list to `_incoming/<sha256>`; `client:load` places each one, in order, and removes the `_incoming/` copies it used.
- `client:load --update --catalog` makes an existing product's files match a declared list: kept files keep their rows, a new file takes the row of one the list left out, in order (so the links already sent for it deliver the new file), the rest are added and the leftovers removed with their links. A single declared file keeps the behavior of `pnpm db:product-file`, which still replaces exactly one file and refuses a product with several.
